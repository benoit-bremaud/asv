# Business rules — asv

Numbered rules enforced by the domain (`src/domain`). Values are V1 defaults, tunable in one place.

## Entry and identity

| Rule | Description | Validation |
|---|---|---|
| BR-001 | A pseudo has 3 to 20 characters among ASCII letters, French accented letters (`àâäéèêëîïôöùûüÿç`, either case), digits, `_`, `-`, `.`. | Refused otherwise. |
| BR-002 | A pseudo is unique among connected and away sessions, ignoring case and accents (`Hélène` = `helene`). | Refused if taken. |
| BR-003 | Pseudos containing reserved words (`admin`, `modo`, `moderateur`, `asv`), ignoring case and accents, are refused. | Refused. |
| BR-004 | The visitor must tick "I am 18 or older" and declare an age between 18 and 99. | Refused otherwise. |
| BR-005 | Gender is optional: woman, man or unspecified (default). | — |
| BR-006 | City is optional free text, 0 to 40 characters, trimmed, following BR-090. | Truncated input refused. |
| BR-007 | At most 5 entry attempts per IP in any 60 seconds. | Further attempts refused until one leaves the window. |
| BR-008 | An IP or pseudo under an active ban cannot enter. | Refused with ban end time. |

## Session and reconnection (ADR-0009, ADR-0011)

Values are owned here. Rationale lives in the ADRs.

| Rule | Description |
|---|---|
| BR-010 | The client sends a heartbeat every 25 s. No heartbeat for 60 s means disconnected. |
| BR-011 | A disconnected session becomes Away for at most 5 minutes. |
| BR-012 | An away session keeps its pseudo, rooms and private windows, and shows "away" to others. |
| BR-013 | Up to 50 private messages are buffered for an away session, oldest dropped first. |
| BR-014 | Resuming requires the current resume token. The token rotates at each resume. |
| BR-015 | After 5 minutes away, the session closes as if the chatter had left. |

## Rooms

| Rule | Description |
|---|---|
| BR-020 | A message has 1 to 500 characters after trimming. |
| BR-090 | Free text (room and private messages, BR-020; city, BR-006) is refused when it holds an invisible or direction-changing character: controls `\p{Cc}` (C0, DEL, C1, tab and line breaks included), the Arabic letter mark U+061C, U+200B, the marks U+200E and U+200F, the line and paragraph separators U+2028 and U+2029, the embeddings and overrides U+202A–202E, U+2060–2064, the isolates U+2066–2069, the deprecated format characters U+206A–206F, U+FEFF, the interlinear annotations U+FFF9–FFFB, and the characters that display as blanks or nothing: soft hyphen U+00AD, U+034F, the Hangul fillers U+115F, U+1160, U+3164 and U+FFA0, U+180E and the blank braille pattern U+2800. The joiners U+200C and U+200D stay allowed (emoji sequences, Persian). A message gives the refusal `invalidText`, a city the entry `invalid`. Text is checked after trimming, never altered. Pseudos and room names already allow none of them (BR-001, BR-030). The web client runs the same pure check before sending: the message composers and the entry form keep sending disabled with a notice and the text in the field. Issue #91, owner choices B+A (475/500, 460/500), then client check A (405/500) and widened set A (440/500). |
| BR-021 | Flood limit: at most 5 accepted messages per 10 seconds per session, across rooms and DMs. Refused messages do not count. |
| BR-022 | Smiley codes (for example `:)`, `:caramel:`) render from a fixed whitelist. Text is never rendered as HTML. |
| BR-023 | A room holds at most 50 members, away members included. |
| BR-024 | A session is in at most 10 rooms at once, created rooms included. |
| BR-030 | A user room name has 3 to 30 characters among the BR-001 characters, `'`, `&`, `!`, `?` and single spaces between words, contains at least one letter or digit, follows BR-003, and is unique among rooms ignoring case, accents, spaces and punctuation (`Paris.` is taken by `Paris`). |
| BR-031 | A session can own at most one user room at a time. Ownership ends when the owner leaves the room, which then has no owner until it is deleted. |
| BR-032 | A user room is deleted when its last member leaves or closes. |
| BR-033 | Official rooms (themed, regional) are defined in configuration and never deleted. |
| BR-034 | A newcomer sees only messages posted after joining. No history. |

## Private conversations and ignore

| Rule | Description |
|---|---|
| BR-040 | A chatter linked to an account can open a private window with any connected or away chatter also linked to an account (ADR-0012). |
| BR-041 | If either chatter ignores the other, the sender's window opens and messages are silently dropped. |
| BR-042 | Ignore lasts for the session and covers room messages and private messages both ways: neither chatter sees the other's messages. The ignored chatter is never told. |
| BR-043 | A chatter can open at most 3 private windows at once (brick 6 owner choice B, 405/500; the trust tiers of #28 will raise it with good behaviour). Closing a window frees a slot; the other side is not told, and a new message reopens it on both sides. A new conversation is refused with `targetBusy` when the receiver already has 3 open windows (brick 6 review, owner choice C, 370/500), so no group can force windows open on one chatter; the refusal says nothing about ignores. |
| BR-044 | A chatter can ignore at most 100 chatters per session. |

## Moderation

| Rule | Description |
|---|---|
| BR-050 | Report reasons: harassment, seems minor, spam, illegal content, other. |
| BR-051 | A report stores the reason, an excerpt of at most 500 characters, up to 20 context lines the reporter saw, author and target pseudos. |
| BR-052 | A chatter can file at most 5 reports per 10 minutes. |
| BR-053 | Ban durations: 1 hour, 24 hours, 7 days. A ban targets a keyed IP hash and the pseudo. |
| BR-054 | Only a session with `isModerator` can list reports (`listOpenReports`, `listAlertedReports`), close reports, expel, remove a room (`removeRoom`) or raise an authority alert. |
| BR-055 | Every moderation action records the moderator name and time. |
| BR-056 | A moderator invitation is single use and expires after 24 hours. |
| BR-057 | A report is closed with one outcome: no action, warned, expelled, suspended, severe deletion, room removed. The AI triage never closes a report (ADR-0010). |
| BR-091 | Removed by brick 8b (#210), replaced by BR-093 to BR-099; kept as the record of brick 8a (#209): a session gets `isModerator` when its `enter` carries a token equal, in constant time, to the server's `ASV_MODERATOR_TOKEN` (32 characters or more, generated with `openssl rand -hex 32`). After 5 wrong tokens from one IP within 10 minutes, every grant from that IP answers `entryRefused(rate)` until the window slides. The server refuses to start with the token and `ASV_TUNNEL=1` together. Actions record the name `owner`. |
| BR-092 | Removed by brick 8c (#211), replaced by BR-102; kept as the record of brick 8a (#209): without AI triage, open reports are listed oldest first. Severe deletion, room removal and the decision e-mail to the reporter are not offered before brick 8c. |
| BR-093 | Invitation and revocation routes (`POST /mod/invitations`, `DELETE /mod/moderators/<name>`) require `Authorization: Bearer` equal in constant time to `ASV_OWNER_SECRET`; the secret is the guard. The same guard covers `POST /mod/authority-filings` (BR-104). They also accept only a loopback peer, a defence in depth that the Vite proxy and cloudflared bypass, so the secret must never be relaxed. Unset secret: the routes answer 404. A secret shorter than 32 characters stops the server at start. |
| BR-094 | A moderator name is 2 to 20 characters among `A-Z a-z 0-9 _ -`, compared case-insensitively. Enrolling again under a name replaces its credential (lost device); one credential per name. Revoking a name deletes its credential and its pending invitations; a session already signed in keeps its rights until it closes (ADR-0008). |
| BR-095 | A successful passkey sign-in returns a grant: name, expiry 60 seconds and a 128-bit random nonce, signed with HMAC-SHA256 under a 256-bit key the server draws at start and never stores (a restart voids pending grants). `enter` with a valid, unexpired grant whose nonce is unused gets `isModerator` and `moderatorName`; the nonce is consumed only when `entered` is sent, so a refused entry (pseudo taken, ban, age) leaves the grant usable until it expires. The hub keeps used nonces until their expiry. The session keeps both for its life, resume included (`resumed.isModerator`, `resumed.moderatorName`). Wrong, expired or replayed grants answer `entryRefused(notModerator)`. |
| BR-096 | After 5 refused grants or owner secrets from one IP within 10 minutes, further ones from that IP are refused (`entryRefused(rate)` or `429`) until the window slides. Each `/mod` ceremony route takes a token from a per-IP bucket of 10 refilled at 1 every 6 seconds; at most 200 challenges are pending in total, beyond which options answer `503` with `Retry-After: 10`. Registration and authentication challenges are single use and kept 5 minutes. |
| BR-097 | Every `/mod/*` route answers 404 when the transport runs with `ASV_TUNNEL=1`. The entry screen shows "connexion modérateur" only when `GET /mod/status` answers 200, so the link stays hidden behind the tunnel: moderation stays closed to testers until the owner opens it once the impact assessment is signed (BR-108). |
| BR-098 | WebAuthn uses the RP ID and expected origin configured by `ASV_PUBLIC_ORIGIN` (default `http://localhost:5173`, its host name as RP ID), never request headers; the invitation link starts with that origin. The RP ID must be a domain, so local QA runs on `localhost`, never an IP address, with `ASV_PUBLIC_ORIGIN=http://localhost:<port>` also listed in `ASV_ALLOWED_ORIGINS`; otherwise the Node transport refuses to start when `ASV_OWNER_SECRET` or `ASV_MODERATOR_FILE` is set, and only warns when neither is. Registration asks `residentKey: "required"` and `userVerification: "required"`; verification requires user verification. |
| BR-099 | Moderator names, credential ids and public keys are encrypted at rest in the moderator file `ASV_MODERATOR_FILE` (ADR-0017, 0600, rewritten through a temporary file and a rename); invitations keep the encrypted name and a SHA-256 of a 256-bit random token. Without `ASV_MODERATOR_FILE` the store is in memory (development and tests). |
| BR-100 | Before a report leaves asv for triage (ADR-0010, ADR-0019), every pseudo is replaced by a neutral label written `[A]`, `[B]`, `[C]`… in order of first appearance: the author of each line, the target, and every connected or away pseudo found in the text as a whole word, compared ignoring case and accents as BR-002 does. E-mail addresses become `[e-mail]` and phone numbers `[téléphone]`. The label map is kept encrypted with the triage, and the queue shows the summary with the legend "[A] = ‹pseudo›" as text only. Only the reason, the target kind and the labelled lines are sent: never an IP, account id, room name or date. |
| BR-101 | The triage answer is accepted only when it is JSON with `category` in harassment, sexualMinor, threat, hate, spam, illegalOther, none; `urgency` in low, medium, high; and `summary` of 1 to 200 characters following BR-090. One call, 10-second timeout, no retry; the adapter sends the lines as a JSON array inside a fixed system prompt. A refused, late or invalid answer, a missing key, more than 200 triage calls in the current UTC day, or more than 20 calls in that day for one reporter (keyed IP hash, or account id for a member), leaves urgency `unknown` and no summary; the hub checks both caps before calling. Urgency floor by reason: a `seemsMinor` or `illegalContent` report is never below medium. The AI never closes or changes a report beyond its triage fields (BR-057). |
| BR-102 | Open reports are listed by urgency (high, medium, unknown, low), then oldest first; an `unknown` report sorts at its reason's floor (BR-101), so a `seemsMinor` or `illegalContent` report is never below medium. The AI category and summary are shown as "tri automatique, à vérifier", as text only. |
| BR-103 | A severe expel (offences listed in LCEN art. 6 IV-A and threats to life or safety, as BR-078) is available on a chatter or message report. A target with an account is deleted at once with its e-mail hash blocked 6 months (BR-078) and a statement of reasons (BR-076); every target gets the 7-day ban on the captured keyed IP hash and pseudo, and every session and away record of the account or pseudo is closed. Outcome `severeDeleted`. A target who deleted their own account before the decision leaves no e-mail hash to block: an accepted limit, only the IP and pseudo ban apply (owner choice 2026-11-13). |
| BR-104 | A moderator may raise an authority alert when closing a report (`closeReport`, `expel`, `removeRoom`, `confirmSuspension`) with an offence category (child abuse, threat to life, terrorism, hate or violence, harassment, other listed offence, `security-and-rgpd.md` §6) that the moderator picks, never copied from the AI category. On a severe expel the alert is preselected and a category is required; the moderator unticks it only deliberately. When life is at stake the moderator may call 17 or 112 directly; the owner records that call as the channel. asv stores one alert per report (report id, offence category, moderator, date, status `pending`) and e-mails `ASV_CONTACT_EMAIL` the report id and category only, never content or pseudos, retried every 10 minutes for at most 7 days. The owner files through the official channel (procedure in `security-and-rgpd.md` §6) and records it with `pnpm mod:filed <reportId> <channel> <reference>` (owner secret and loopback, BR-093), which sets the alert to `filed`. Channel is one of PHAROS, 17, 112, PointDeContact; reference is 1 to 100 characters following BR-090; an already filed alert answers 409, an unknown report or a report without alert 404. Moderators see alerted reports in the "alertes" tab of the queue (`listAlertedReports`). |
| BR-105 | A report with an authority alert, and the alert, are kept 1 year after the report closes instead of 6 months (owner proposal, no binding text), encrypted at rest (ADR-0017). |
| BR-106 | Room removal applies to a room report whose user room still exists: the room closes, its members get `roomClosed`, its name is freed, outcome `roomRemoved`. An official room, or a user room already gone, answers `warning(reportInvalid)`; the moderator then closes with another outcome. |
| BR-107 | A report filed by a member keeps the reporter's account id, never the e-mail. When the report closes and that account still exists, asv e-mails the reporter the decision in general terms (action taken or not), whether automated means were used, and how to contest (DSA art. 16(5)); never the target's pseudo or sanction. The address is read at sending time and kept only until the mail is accepted, retried at most 7 days. A guest reporter gets no e-mail (owner choice 2026-11-13). |
| BR-108 | Behind the tester tunnel moderation stays closed (BR-097, `canReport = false`) after brick 8c; opening it to testers is a separate owner decision once the impact assessment is signed. |

## Accounts and strikes (ADR-0012, ADR-0013, ADR-0014)

| Rule | Description |
|---|---|
| BR-070 | A sign-in code has six digits, is single use, valid 10 minutes, stored as a keyed hash, and invalidated after 5 wrong tries. |
| BR-071 | E-mail addresses from known disposable domains are refused (maintained list). |
| BR-072 | At most 3 sign-in codes per e-mail and 10 per IP per hour, and 60 seconds between two codes for the same e-mail. After 20 wrong codes for one e-mail within 24 hours, no new code is sent for that e-mail until the oldest of those tries is 24 hours old (owner choice 2026-10-23, 435/500, against slow brute force from rotating IPs). Over the IP quota the request is refused with a reason; a blocked e-mail, the e-mail quota, the cooldown or the wrong-try cap get the same "code sent" answer with no code sent (ADR-0013 amendment). |
| BR-073 | A remembered device gets a random token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie valid 30 days, set over HTTPS in exchange for a single-use device claim valid 60 seconds. The server keeps only hashes. |
| BR-074 | A warning on a chatter with an account adds a strike. A strike expires after 90 days. |
| BR-075 | While an account has 3 or more active strikes and no decision, the moderator panel proposes a 7-day suspension. Without confirmation, nothing happens. |
| BR-076 | Every suspension or deletion decided by a moderator e-mails a statement of reasons (DSA art. 17). The address is kept only until the mail is accepted, retried for at most 7 days. |
| BR-077 | A suspension deletes the account, blocks a keyed hash of its e-mail for 7 days, closes every session and away record of the account, and bans for 7 days the keyed IP hash and pseudo captured on the report (or of the live session when newer). |
| BR-078 | Severe cases (grooming, threats, child sexual abuse material, incitement to violence) delete the account at once and block the e-mail hash for 6 months (owner proposal, no binding text). The owner promptly informs the authorities of offences listed in LCEN art. 6 IV-A and of any threat to life or safety (DSA art. 18). |
| BR-079 | An account unused for 2 years is deleted after an e-mail notice (owner proposal, GDPR art. 5(1)(e)). |
| BR-080 | A member may delete their account at any time. If strikes are active, a keyed e-mail hash and the strike expiry dates are kept until the last one expires, and restored if the same e-mail creates a new account. |
| BR-081 | Every account deletion writes, in the same transaction, a legal retention record to the vault: account id, e-mail, creation (= verification) and closing dates. The account id is purged 1 year and the rest 5 years after closing (decree 2021-1362 arts. 2 and 3, ADR-0014). Session pseudonyms stay only in the connection log (BR-060). Never a deletion reason, strike or report. |
| BR-082 | Only the owner reads the vault and the connection log, to answer an authority entitled by law. Each read appends an access entry: date, request reference, legal basis, ids returned. Access entries are kept 5 years after the read, then purged by the daily alarm. No use case, moderation tool or AI reads them. |
| BR-083 | Every personal or sensitive stored value is encrypted at application level (AES-256-GCM, versioned keys in secrets) and looked up by keyed hash. Vault values and access entries are sealed to the owner public key, so the application cannot read them back. Only random ids, dates and counters stay clear (ADR-0017). Temporary exception: the tester log file of BR-084, plaintext until brick 9 (ADR-0018). |
| BR-087 | While a sign-in code is pending, the web client keeps in `sessionStorage` the code deadline only (the `codeSent` time plus 10 minutes, never the e-mail nor the code). The server keeps the pending code under the session id, which a resume keeps. A `resumed` without an account leaves an open code step as it is (open or closed); after a page reload, it reopens the code step if the deadline has not passed. `accountLinked`, a warning that leads back to the e-mail step (`codeExpired`, `codeExhausted`, `codeMissing` and the others of `web-ui/06`), "nouveau code", `entered`, `resumeRefused`, `expelled`, leaving or the deadline passing clear it (issue #72). |

## Retention (legal basis in security-and-rgpd.md §1–2)

| Rule | Description |
|---|---|
| BR-060 | One connection line per socket connection (entry or resume): random connection id, IP and source port if available, protocols, pseudo, account id if any, start and end times. One contribution line per creation of a room message, private message or user room name: connection id and protocols (decree 2021-1362 arts. 5 2° and 7). While a Prime Minister's injunction under CPCE L34-1 III is in force (checked each October), the contribution line also carries the content id, the operation, its date and time (art. 6 2°; the author's identifier is the pseudo or account id on the connection line). Never the content. Each line kept 1 year from its connection or contribution, then deleted (LCEN art. 6 V-A). |
| BR-061 | Closed reports are kept 6 months, 1 year with an authority alert (BR-105), then deleted. |
| BR-062 | Expired bans are deleted 30 days after their end. |
| BR-084 | While asv is exposed to testers through the tunnel (ADR-0018), the Node transport appends connection and contribution lines to a local JSONL file outside the repository, one JSON object per line, and appends to a second JSONL file, sealed to the owner key (BR-083), an opening record when an account is created (account id, e-mail, creation date) and a closing record when it is deleted (BR-081). Since in-memory accounts end with the process, even on a crash, at start-up every opening record without a closing record gets one dated at that start-up, and so does every connection line left open, so retention never depends on a graceful stop. The opening record is written before the account is saved. A purge rewrites through a temporary file and a rename; unreadable lines and dates are kept, never dropped. At start-up and once a day it removes log lines whose connection start or contribution date is more than 1 year old, and applies the BR-081 purge to the vault file. The owner reads these files only under BR-082 and records an access entry by hand. Without the file settings, memory is used (development and tests). |

## Transport security (ADR-0018)

| Rule | Description |
|---|---|
| BR-085 | The client IP and source port on the connection line come from the socket. Only when the transport runs with the tunnel flag, the IP comes from `CF-Connecting-IP` (no source port then). The flag requires the server to listen on loopback only; the transport refuses to start otherwise. The header must hold exactly one valid IPv4 or IPv6 address, otherwise the socket address is used. `X-Forwarded-*` headers are never trusted. The tunnel host name is added to the allowed Origins. |
| BR-086 | Every HTTP response of the Hono app served by the Node transport from the production build (WebSocket upgrade refusals are not documents) carries `Content-Security-Policy: default-src 'self'; connect-src 'self'; img-src 'self' data:; style-src 'self'; script-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), serial=(), hid=(), display-capture=(), browsing-topics=()` (no powerful feature the chat never uses, #69), plus the other defaults of Hono `secureHeaders` (`X-Frame-Options: SAMEORIGIN`, same-origin COOP and CORP, `X-XSS-Protection: 0` and similar). When the `secureCookie` option is on (set by the tunnel run, and always in production), the device cookie carries `Secure` (BR-073) and responses add `Strict-Transport-Security: max-age=15552000`. The Vite dev server is not covered: testers always get the built bundle. |
| BR-088 | Every socket has a frame budget, a token bucket of 40 tokens refilled at 20 per second; every frame takes one token, `ping` included, before any parsing. A frame that finds the bucket empty closes the socket with code 1008 (policy violation) and reason `tooManyFrames`, unanswered. Five invalid frames in a row (not JSON, or refused by the `clientMessage` schema, or over the hub cap) close the socket the same way with reason `invalidFrames`; a valid frame resets the count, and a `ping`, answered by the transport, neither counts nor resets it. The close then follows the ordinary "socket closed" path (BR-011): a member goes away and may resume. The web client sends at most one frame per user action plus a `ping` every 25 s, so it never reaches either limit. |
| BR-089 | Before a WebSocket upgrade with an allowed Origin, the transport checks three limits on the client IP of BR-085: at most 20 open sockets per IP, at most 500 open sockets in total, and an upgrade budget per IP, a token bucket of 20 tokens refilled at 1 per second, where every checked upgrade takes one token, refused or not. A refusal answers before any socket exists, so no connection line is written: `429 Too Many Requests` with `Retry-After: 10` for the per-IP cap or an empty budget, `503 Service Unavailable` with `Retry-After: 10` for the total cap, then the socket is destroyed once the answer is sent. A socket closing releases its place. A socket that holds no session (never entered nor resumed, or left) for 10 minutes, measured by the hub tick to within one tick, is closed with code 1008 and reason `unbound`, then follows the ordinary "socket closed" path. The web client opens one socket per tab, reconnects at most once a second and pings every 25 s, so several tabs and several people behind one home NAT stay within the limits (issue #23). |
